## 一、数据库概览与生态关系

### 1.1 主流数据库家族

理解数据库的「血缘关系」是快速掌握语法差异的关键。多数国产数据库基于 PostgreSQL 或 MySQL/Oracle 内核演进，语法可对标。

| 数据库 | 厂商/社区 | 内核来源 | 语法对标 |
|------|------|------|------|
| **MySQL** | Oracle（开源） | 自研 | 自身（MySQL 方言） |
| **PostgreSQL** | 社区（开源） | 自研 | SQL 标准最贴近 |
| **SQL Server** | 微软 | 自研（源自 Sybase） | 自身（T-SQL 方言） |
| **Oracle** | 甲骨文 | 自研 | 自身（PL/SQL 方言） |
| **达梦 DM** | 武汉达梦 | 自研 | **高度兼容 Oracle** |
| **人大金仓 KingbaseES** | 人大金仓 | **基于 PostgreSQL** | 兼容 PostgreSQL + 部分 Oracle |
| **openGauss** | 华为（开源） | **基于 PostgreSQL 9.2 演进** | 兼容 PostgreSQL |
| **GaussDB** | 华为云 | openGauss / MySQL 两种模式 | 可配 PostgreSQL/MySQL 兼容 |
| **OceanBase** | 蚂蚁（开源） | 自研 | 兼容 MySQL 或 Oracle（双模式） |
| **TiDB** | PingCAP（开源） | 自研 | **高度兼容 MySQL** |
| **PolarDB** | 阿里云 | MySQL/PG 两版 | MySQL 版 / PostgreSQL 版 |
| **GBase** | 南大通用 | 自研 | 8a（分析型）、8s（类 Oracle） |
| **瀚高 HighGo** | 瀚高 | 基于 PostgreSQL | 兼容 PostgreSQL |
| **神通 OSCAR** | 神舟通用 | 自研 | 兼容 Oracle |
| **崖山 YashanDB** | 深圳计算科学研究院 | 自研 | 兼容 Oracle |

### 1.2 生态关系速记

```
                    ┌─ PostgreSQL ─┬─ KingbaseES（金仓）
                    │              ├─ openGauss / GaussDB
                    │              ├─ HighGo（瀚高）
                    │              └─ PolarDB-PG 版
SQL 标准 ───────────┤
                    ├─ MySQL ─────┬─ TiDB
                    │             ├─ OceanBase（MySQL 模式）
                    │             └─ PolarDB-MySQL 版
                    ├─ Oracle ────┬─ 达梦 DM
                    │             ├─ OceanBase（Oracle 模式）
                    │             ├─ GBase 8s
                    │             └─ 神通 OSCAR
                    └─ Sybase ──── SQL Server（T-SQL）
```

> **结论**：如果你的应用跑在 PostgreSQL 上，迁移到金仓/openGauss 基本无痛；跑在 Oracle 上，迁移到达梦/神通最省力；跑在 MySQL 上，TiDB/OceanBase 是平替。

## 二、SQL 标准与共性语法总结

好消息是：**绝大多数日常 SQL 在各数据库间是通用的**。以下语法在 MySQL、PostgreSQL、SQL Server、Oracle 及国产数据库中几乎完全一致，可直接使用。

### 2.1 完全通用的查询语法

```sql
-- 基本查询
SELECT column1, column2 FROM table_name;

-- 条件过滤
SELECT * FROM users WHERE age > 18 AND status = 'active';

-- 排序
SELECT * FROM users ORDER BY created_at DESC, id ASC;

-- 聚合函数
SELECT dept_id, COUNT(*), SUM(salary), AVG(salary), MAX(salary), MIN(salary)
FROM employees GROUP BY dept_id;

-- 聚合过滤（HAVING）
SELECT dept_id, COUNT(*) AS cnt
FROM employees
GROUP BY dept_id
HAVING COUNT(*) > 10;

-- 多表连接
SELECT u.name, o.order_no
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

SELECT u.name, o.order_no
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;

-- 子查询
SELECT * FROM users WHERE dept_id IN (SELECT id FROM depts WHERE active = 1);

-- 去重
SELECT DISTINCT city FROM users;

-- 联合查询
SELECT id, name FROM users
UNION            -- 去重合并
SELECT id, name FROM customers;

SELECT id, name FROM users
UNION ALL        -- 不去重合并（性能更好）
SELECT id, name FROM customers;

-- 条件表达式
SELECT name,
       CASE WHEN score >= 90 THEN 'A'
            WHEN score >= 80 THEN 'B'
            ELSE 'C' END AS grade
FROM students;
```

### 2.2 完全通用的写操作

```sql
-- 插入
INSERT INTO users (name, age) VALUES ('张三', 25);
INSERT INTO users (name, age) VALUES ('张三', 25), ('李四', 30);  -- 多行插入（主流均支持）

-- 更新
UPDATE users SET age = 26 WHERE name = '张三';

-- 删除
DELETE FROM users WHERE id = 10;

-- 条件删除/更新
DELETE FROM users WHERE age > 60;
```

### 2.3 通用但需注意的差异点

| 语法 | 共性 | 差异说明 |
|------|------|----------|
| `SELECT`/`INSERT`/`UPDATE`/`DELETE` | ✅ 完全通用 | 无 |
| `JOIN`/`GROUP BY`/`HAVING`/`ORDER BY` | ✅ 完全通用 | 无 |
| `CASE WHEN` | ✅ 完全通用 | 各库推荐使用它替代方言函数 |
| `CAST`/`COALESCE` | ✅ 通用 | 建议优先用标准函数 |
| 分页 | ❌ 差异大 | 见[第四章](#四分页与限制行数top-n) |
| 字符串/日期函数 | ⚠️ 部分差异 | 见[第六、七章](#六字符串函数对比) |
| 自增主键 | ❌ 差异大 | 见[第五章](#五自增主键与序列) |

### 2.4 编写跨库 SQL 的建议

1. **能用标准 SQL 就不用方言函数**（如用 `COALESCE` 而非 `ISNULL`/`NVL`/`IFNULL`）
2. **用 `CASE WHEN` 替代 `IF()`/`DECODE()` 等方言**
3. **用 `CAST(x AS type)` 替代 `CONVERT`/`::` 等方言**
4. **分页、自增、字符串函数等核心差异，封装到 ORM 或数据访问层**（如 EF Core 的 `Take/Skip` 自动翻译）

## 三、数据类型对比

### 3.1 数值类型

| 用途 | MySQL | PostgreSQL | SQL Server | Oracle | 达梦/金仓等国产 |
|------|------|------|------|------|------|
| 整数 | `INT` / `INTEGER` | `INTEGER` / `INT` | `INT` | `NUMBER(10)` | 兼容对标库 |
| 小整数 | `TINYINT` / `SMALLINT` | `SMALLINT` | `TINYINT` / `SMALLINT` | `NUMBER(3)` | 兼容对标库 |
| 大整数 | `BIGINT` | `BIGINT` | `BIGINT` | `NUMBER(19)` | 兼容对标库 |
| 精确小数 | `DECIMAL(p,s)` | `NUMERIC(p,s)` | `DECIMAL(p,s)` | `NUMBER(p,s)` | 兼容对标库 |
| 浮点数 | `FLOAT` / `DOUBLE` | `REAL` / `DOUBLE PRECISION` | `FLOAT` / `REAL` | `BINARY_FLOAT` | 兼容对标库 |
| 金额（推荐） | `DECIMAL(18,2)` | `NUMERIC(18,2)` | `DECIMAL(18,2)` | `NUMBER(18,2)` | 兼容对标库 |

> **共识**：金额一律用 `DECIMAL/NUMERIC`，禁用 `FLOAT`（精度丢失）。

### 3.2 字符串类型

| 用途 | MySQL | PostgreSQL | SQL Server | Oracle | 说明 |
|------|------|------|------|------|------|
| 变长字符串 | `VARCHAR(n)` | `VARCHAR(n)` | `VARCHAR(n)` | `VARCHAR2(n)` | 最常用 |
| 定长字符串 | `CHAR(n)` | `CHAR(n)` | `CHAR(n)` | `CHAR(n)` | 少用 |
| 长文本 | `TEXT` | `TEXT` | `VARCHAR(MAX)` | `CLOB` | 大文本 |

> Oracle 用 `VARCHAR2`（推荐）而非 `VARCHAR`；达梦同时支持 `VARCHAR` 和 `VARCHAR2`。

### 3.3 日期时间类型

| 用途 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|------|------|------|------|
| 日期 | `DATE` | `DATE` | `DATE` | `DATE` |
| 时间 | `TIME` | `TIME` | `TIME` | —（用 TIMESTAMP） |
| 日期+时间 | `DATETIME` / `TIMESTAMP` | `TIMESTAMP` | `DATETIME2` / `DATETIME` | `TIMESTAMP` / `DATE` |
| 带时区 | `TIMESTAMP` | `TIMESTAMPTZ` | `DATETIMEOFFSET` | `TIMESTAMP WITH TIME ZONE` |

> 注意：MySQL 的 `TIMESTAMP` 有 2038 年问题，推荐 `DATETIME`；Oracle 的 `TIMESTAMP` 含时间，`DATE` 也含时分秒（与其他库不同）。

### 3.4 布尔类型

| 数据库 | 布尔类型 | 说明 |
|------|------|------|
| PostgreSQL | `BOOLEAN` | 真布尔，值 `true`/`false` |
| MySQL | `BOOLEAN` = `TINYINT(1)` | 实际是 0/1 |
| SQL Server | `BIT` | 值 0/1/NULL |
| Oracle | 无布尔类型 | 用 `NUMBER(1)` 或 `CHAR(1)` |
| 达梦 | 支持 `BIT` / 兼容 | 类 Oracle + 扩展 |

### 3.5 大对象（LOB）

| 数据库 | 二进制大对象 |
|------|------|
| MySQL | `BLOB` / `LONGBLOB` |
| PostgreSQL | `BYTEA` / `OID` |
| SQL Server | `VARBINARY(MAX)` |
| Oracle | `BLOB` |

## 四、分页与限制行数（Top-N）

**分页是各数据库差异最大的语法点之一**，也是迁移最容易踩坑的地方。

### 4.1 限制前 N 行

| 数据库 | 语法 |
|------|------|
| MySQL | `SELECT ... LIMIT 10` |
| PostgreSQL | `SELECT ... LIMIT 10` |
| SQL Server | `SELECT TOP 10 ...` |
| Oracle（旧） | `SELECT ... WHERE ROWNUM <= 10` |
| Oracle 12c+ | `SELECT ... FETCH FIRST 10 ROWS ONLY` |
| 达梦 DM | 兼容 `ROWNUM`、`LIMIT`、`FETCH FIRST` 多种写法 |
| KingbaseES/openGauss | `LIMIT 10`（兼容 PG） |

### 4.2 分页查询（跳过 m 条，取 n 条）

| 数据库 | 语法 |
|------|------|
| MySQL | `SELECT * FROM t ORDER BY id LIMIT 10, 20`（注意：10 是 offset） |
| PostgreSQL | `SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 10` |
| SQL Server 2012+ | `SELECT * FROM t ORDER BY id OFFSET 10 ROWS FETCH NEXT 20 ROWS ONLY` |
| Oracle 12c+ | `SELECT * FROM t ORDER BY id OFFSET 10 ROWS FETCH NEXT 20 ROWS ONLY` |
| Oracle（旧） | 三层嵌套 `ROWNUM` 写法（复杂） |
| 达梦 DM | 支持 `LIMIT` 和 Oracle 的 `OFFSET/FETCH` |
| KingbaseES/openGauss | `LIMIT 20 OFFSET 10` |

**示例对照（取第 11-30 条）：**

```sql
-- MySQL
SELECT * FROM users ORDER BY id LIMIT 10, 20;

-- PostgreSQL / KingbaseES / openGauss
SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 10;

-- SQL Server / Oracle 12c+
SELECT * FROM users ORDER BY id OFFSET 10 ROWS FETCH NEXT 20 ROWS ONLY;

-- 达梦 DM（二选一，均支持）
SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 10;
SELECT * FROM users ORDER BY id OFFSET 10 ROWS FETCH NEXT 20 ROWS ONLY;
```

### 4.3 分页共性提醒

1. **分页必须配合 `ORDER BY`**，否则结果顺序不稳定。
2. MySQL 的 `LIMIT m, n` 中 **m 是偏移量**，与 PG 的 `LIMIT n OFFSET m` 语义容易混淆。
3. 大数据量深分页（`OFFSET` 很大）各库性能都差，建议用「游标/`WHERE id > 上次最大值`」优化。

## 五、自增主键与序列

### 5.1 建表时的自增列

| 数据库 | 语法 |
|------|------|
| MySQL | `id INT AUTO_INCREMENT PRIMARY KEY` |
| PostgreSQL | `id SERIAL PRIMARY KEY` 或 `id INT GENERATED ALWAYS AS IDENTITY` |
| SQL Server | `id INT IDENTITY(1,1) PRIMARY KEY` |
| Oracle 12c+ | `id NUMBER GENERATED BY DEFAULT AS IDENTITY` |
| Oracle（旧） | 无自增，用 `SEQUENCE` + 触发器 |
| 达梦 DM | 支持 `IDENTITY(1,1)` 和 `AUTO_INCREMENT` |
| KingbaseES/openGauss | `SERIAL` 或 `IDENTITY`（兼容 PG） |
| OceanBase/TiDB | `AUTO_INCREMENT`（兼容 MySQL） |

**示例：**

```sql
-- MySQL / TiDB / OceanBase(MySQL模式)
CREATE TABLE users (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50)
);

-- PostgreSQL / KingbaseES / openGauss
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(50)
);

-- SQL Server
CREATE TABLE users (
  id BIGINT IDENTITY(1,1) PRIMARY KEY,
  name VARCHAR(50)
);

-- 达梦 DM（两种均可）
CREATE TABLE users (
  id BIGINT IDENTITY(1,1) PRIMARY KEY,
  name VARCHAR(50)
);
```

### 5.2 获取刚插入的自增值

| 数据库 | 语法 |
|------|------|
| MySQL | `SELECT LAST_INSERT_ID();` |
| PostgreSQL | `INSERT ... RETURNING id;` 或 `SELECT lastval();` |
| SQL Server | `SELECT SCOPE_IDENTITY();` 或 `OUTPUT INSERTED.id` |
| Oracle | `INSERT ... RETURNING id INTO :var;` 或 `seq.CURRVAL` |
| 达梦 | 兼容 `IDENTITY` 相关函数，或序列 `seq.CURRVAL` |

> EF Core/Dapper 等 ORM 会自动处理自增值回填，业务代码一般无需手写。

### 5.3 序列（Sequence）

Oracle 及老式写法用独立序列对象：

```sql
-- Oracle / 达梦 / 神通
CREATE SEQUENCE seq_users START WITH 1 INCREMENT BY 1;
INSERT INTO users (id, name) VALUES (seq_users.NEXTVAL, '张三');
```

| 取长度（字符） | `CHAR_LENGTH(s)` | `LENGTH(s)` | `LEN(s)` | `LENGTH(s)` | `CHAR_LENGTH(s)` |
| 取长度（字节） | `LENGTH(s)` | `OCTET_LENGTH(s)` | `DATALENGTH(s)` | `LENGTHB(s)` | — |
| 转大写 | `UPPER(s)` | `UPPER(s)` | `UPPER(s)` | `UPPER(s)` | ✅ 通用 |
| 转小写 | `LOWER(s)` | `LOWER(s)` | `LOWER(s)` | `LOWER(s)` | ✅ 通用 |
| 去空格 | `TRIM(s)` | `TRIM(s)` | `TRIM(s)` | `TRIM(s)` | ✅ 通用 |
| 去左空格 | `LTRIM(s)` | `LTRIM(s)` | `LTRIM(s)` | `LTRIM(s)` | ✅ 通用 |
| 去右空格 | `RTRIM(s)` | `RTRIM(s)` | `RTRIM(s)` | `RTRIM(s)` | ✅ 通用 |

| 定位子串 | `LOCATE(a,s)` / `INSTR` | `POSITION(a IN s)` | `CHARINDEX(a,s)` | `INSTR(s,a)` | — |
| 填充 | `LPAD(s,n,c)` | `LPAD(s,n,c)` | `FORMAT`/自定义 | `LPAD(s,n,c)` | — |

### 6.2 关键差异示例

```sql
-- 取前 3 个字符
-- MySQL / PostgreSQL / SQL Server
SELECT SUBSTRING('hello', 1, 3);       -- 'hel'
-- Oracle / 达梦（SUBSTR 亦可）
SELECT SUBSTR('hello', 1, 3);          -- 'hel'

-- 字符串长度（含中文，注意字符 vs 字节）
-- MySQL: CHAR_LENGTH 按字符
SELECT CHAR_LENGTH('你好');             -- 2
-- SQL Server: LEN 按字符
SELECT LEN('你好');                     -- 2
-- PostgreSQL: LENGTH 按字符
SELECT LENGTH('你好');                  -- 2
-- Oracle: LENGTH 按字符
SELECT LENGTH('你好');                  -- 2
```

## 七、日期时间函数对比

### 7.1 获取当前时间

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|------|------|------|------|
| 当前日期时间 | `NOW()` | `NOW()` / `CURRENT_TIMESTAMP` | `GETDATE()` | `SYSDATE` |
| 当前日期 | `CURDATE()` | `CURRENT_DATE` | `CAST(GETDATE() AS DATE)` | `TRUNC(SYSDATE)` |
| 当前时间 | `CURTIME()` | `CURRENT_TIME` | `CONVERT(TIME, GETDATE())` | — |

### 7.2 日期运算

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|------|------|------|------|
| 加天数 | `DATE_ADD(d, INTERVAL 7 DAY)` | `d + INTERVAL '7 days'` | `DATEADD(day, 7, d)` | `d + 7` |

| 日期差（天） | `DATEDIFF(d2, d1)` | `d2 - d1` | `DATEDIFF(day, d1, d2)` | `d2 - d1` |

### 7.3 提取日期部分

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle |
|------|------|------|------|------|
| 年份 | `YEAR(d)` | `EXTRACT(YEAR FROM d)` | `YEAR(d)` | `EXTRACT(YEAR FROM d)` |

| 日 | `DAY(d)` | `EXTRACT(DAY FROM d)` | `DAY(d)` | `EXTRACT(DAY FROM d)` |

### 7.4 格式化日期

| 数据库 | 语法 | 示例 |
|------|------|------|
| MySQL | `DATE_FORMAT(d, '%Y-%m-%d')` | `DATE_FORMAT(NOW(), '%Y-%m-%d')` |
| PostgreSQL | `TO_CHAR(d, 'YYYY-MM-DD')` | `TO_CHAR(NOW(), 'YYYY-MM-DD')` |
| SQL Server | `FORMAT(d, 'yyyy-MM-dd')` | `FORMAT(GETDATE(), 'yyyy-MM-dd')` |
| Oracle | `TO_CHAR(d, 'YYYY-MM-DD')` | `TO_CHAR(SYSDATE, 'YYYY-MM-DD')` |

## 八、空值与条件判断

### 8.1 空值处理函数

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle | 标准写法（推荐） |
|------|------|------|------|------|------|
| 空值替换 | `IFNULL(a, b)` | `COALESCE(a, b)` | `ISNULL(a, b)` | `NVL(a, b)` | `COALESCE(a, b)` |
| 多值取第一个非空 | `COALESCE(a,b,c)` | `COALESCE(a,b,c)` | `COALESCE(a,b,c)` | `COALESCE(a,b,c)` | ✅ 通用 |
| 空值判断 | `IS NULL` | `IS NULL` | `IS NULL` | `IS NULL` | ✅ 通用 |

> **强烈推荐统一使用 `COALESCE`**：它是 SQL 标准，四类数据库全部支持，且可传多个参数。

```sql
-- 等价写法（推荐用 COALESCE）
SELECT COALESCE(nickname, name, '匿名') FROM users;
```

### 8.2 条件判断

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle | 推荐 |
|------|------|------|------|------|------|
| 条件表达式 | `CASE WHEN` | `CASE WHEN` | `CASE WHEN` | `CASE WHEN` | ✅ 通用 |
| 简单条件 | `IF(cond,a,b)` | 无（用 CASE） | `IIF(cond,a,b)` | `DECODE(x,a,b)` | 用 `CASE WHEN` |
| 空值专用 | `IFNULL` | — | `ISNULL` | `NVL` | 用 `COALESCE` |

```sql
-- 各库方言（均可用 CASE WHEN 替代）
-- MySQL
SELECT IF(age >= 18, '成年', '未成年') FROM users;
-- SQL Server
SELECT IIF(age >= 18, '成年', '未成年') FROM users;
-- Oracle
SELECT DECODE(status, 1, '启用', 0, '禁用', '未知') FROM users;

-- 通用写法（所有库一致）
SELECT CASE WHEN age >= 18 THEN '成年' ELSE '未成年' END FROM users;
```

## 十、字符串拼接

| 数据库 | 拼接方式 |
|------|------|
| MySQL | `CONCAT(a, b, c)` |
| PostgreSQL | `a \|\| b \|\| c`（也支持 `CONCAT`） |
| SQL Server | `a + b + c`（或 `CONCAT(a,b,c)`） |
| Oracle | `a \|\| b \|\| c` |

```sql
-- MySQL
SELECT CONCAT(first_name, ' ', last_name) FROM users;

-- PostgreSQL / Oracle
SELECT first_name || ' ' || last_name FROM users;

-- SQL Server
SELECT first_name + ' ' + last_name FROM users;
SELECT CONCAT(first_name, ' ', last_name) FROM users;  -- 更安全（自动处理 NULL）
```

> **注意 NULL 陷阱**：SQL Server 用 `+` 拼接时，任一操作数为 NULL 结果就是 NULL；`CONCAT` 则把 NULL 当空串。MySQL 的 `CONCAT` 同样把 NULL 当空串处理。

// EF Core 自动翻译为对应数据库的分页语法
var page = await context.Users
    .OrderBy(u => u.Id)
    .Skip((pageIndex - 1) * pageSize)   // OFFSET

## 十六、性能排查与优化

性能问题排查遵循统一的「五步法」，各数据库的工具与命令不同，但思路一致。

### 16.1 通用排查流程

```
① 定位慢 SQL      → 找到耗时最长的语句（慢查询日志 / 监控 / 等待事件）
② 查看执行计划     → 用 EXPLAIN 看数据库实际怎么执行
③ 定位瓶颈        → 全表扫描？索引失效？锁等待？资源不足？
④ 实施优化        → 加索引 / 改写法 / 调参数 / 分库分表
⑤ 验证效果        → 对比优化前后耗时与执行计划
```

**判断瓶颈的四个维度：**

| 瓶颈类型 | 典型表现 | 优化方向 |
|------|------|------|
| 全表扫描 | 执行计划显示 `ALL`/`Seq Scan`/`Table Scan` | 建索引、改查询条件 |
| 索引失效 | 有索引但未命中 | 避免函数包裹列、隐式转换、前导通配符 |
| 锁等待 | 事务阻塞、超时 | 缩短事务、优化锁粒度 |
| 资源不足 | CPU/内存/IO 打满 | 加资源、调参数、优化 SQL |

### 16.2 执行计划查看（各库对照）

| 数据库 | 查看执行计划 | 查看真实执行耗时 |
|------|------|------|
| MySQL | `EXPLAIN SELECT ...` | `EXPLAIN ANALYZE SELECT ...`（8.0.18+） |
| PostgreSQL | `EXPLAIN SELECT ...` | `EXPLAIN ANALYZE SELECT ...` |
| SQL Server | `SET SHOWPLAN_ALL ON` 或图形计划 | `SET STATISTICS TIME ON` |
| Oracle | `EXPLAIN PLAN FOR ...` + `DBMS_XPLAN.DISPLAY` | 需看 AWR/`V$SQL` |
| 达梦 DM | `EXPLAIN SELECT ...`（兼容 Oracle） | 查看执行计划与耗时 |
| KingbaseES/openGauss | `EXPLAIN ANALYZE SELECT ...`（兼容 PG） | 同 PG |

**执行计划关键信号（各库通用）：**

| 危险信号 | 含义 |
|------|------|
| `ALL`（MySQL）/ `Seq Scan`（PG）/ `Table Scan`（SQL Server） | 全表扫描，优先优化 |
| `Using filesort` / `Using temporary`（MySQL） | 排序/临时表，考虑加索引 |
| 大 `rows` 估算值与实际不符 | 统计信息过期，需更新 |
| `Nested Loop` 且内表扫描大 | 缺连接条件索引 |

### 16.3 MySQL 排查与优化

**定位慢 SQL：**

```sql
-- 查看正在执行的查询
SHOW PROCESSLIST;
SHOW FULL PROCESSLIST;

-- 查看慢查询相关配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;   -- 超过 1 秒记录
```

**EXPLAIN 关键字段解读：**

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
```

| 字段 | 关注点 |
|------|------|
| `type` | 从优到劣：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`；出现 `ALL` 需优化 |
| `key` | 实际使用的索引（NULL 表示没用上） |
| `rows` | 预估扫描行数，越大越慢 |
| `Extra` | `Using filesort`/`Using temporary` 需警惕；`Using index` 表示覆盖索引（最优） |

**InnoDB 关键参数：**

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';   -- 缓冲池，建议占内存 50%-70%
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW STATUS LIKE 'Threads_connected';
```

**常用优化手段：**

- 为 WHERE/JOIN/ORDER BY 字段建合适索引
- 用**覆盖索引**避免回表（`SELECT` 列全在索引中）
- 避免 `SELECT *`
- 深分页用「游标法」：`WHERE id > 上页最大id LIMIT n` 替代大 `OFFSET`
- 避免 `%关键字%` 前导通配符

### 16.4 PostgreSQL 排查与优化

**定位慢 SQL：**

```sql
-- 开启 pg_stat_statements 扩展（最常用）
CREATE EXTENSION pg_stat_statements;

-- 查询最耗时的 SQL
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 查看当前活动查询
SELECT pid, state, query, now() - query_start AS duration
FROM pg_stat_activity
WHERE state = 'active';
```

**执行计划与统计信息：**

```sql
-- 查看执行计划（含真实耗时和 IO）
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

-- 更新表统计信息（执行计划不准时执行）
ANALYZE table_name;

-- 清理死行（VACUUM 回收空间 + 更新统计）
VACUUM ANALYZE table_name;
```

**PG 特有注意点：**

| 问题 | 说明 |
|------|------|
| 表膨胀 | 大量 UPDATE/DELETE 后需 `VACUUM` 回收空间，否则查询变慢 |
| 统计信息过期 | 数据变化大时需 `ANALYZE`，否则执行计划失真 |
| 索引类型 | JSON/全文用 `GIN`，范围用 `B-tree`，模糊搜索用 `pg_trgm` |
| 慢查询日志 | `log_min_duration_statement = 1000`（记录超 1 秒的 SQL） |

### 16.5 SQL Server 排查与优化

**定位慢 SQL（动态管理视图 DMV）：**

```sql
-- 查询最耗时的 SQL（按总耗时排序）
SELECT TOP 10
    qs.total_elapsed_time / 1000000 AS 总耗时秒,
    qs.execution_count AS 执行次数,
    SUBSTRING(st.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
          ELSE qs.statement_end_offset END - qs.statement_start_offset)/2)+1) AS SQL语句
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_elapsed_time DESC;

-- 查看缺失索引建议
SELECT * FROM sys.dm_db_missing_index_details;

-- 查看索引碎片
SELECT * FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED');

-- 查看等待统计（定位瓶颈类型）
SELECT TOP 10 wait_type, wait_time_ms, waiting_tasks_count
FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;
```

**执行计划与 IO 统计：**

```sql
-- 打开 IO/时间统计
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
-- 执行查询后查看「逻辑读取」次数（越少越好）

-- 查看实际执行计划
SET SHOWPLAN_XML ON;   -- 或图形界面 Ctrl+M
```

**优化手段：**

- 缺失索引 → 按 DMV 建议补索引
- 索引碎片率高 → `ALTER INDEX ... REBUILD/REORGANIZE`
- 参数嗅探问题 → 用 `OPTION (RECOMPILE)` 或局部变量规避
- 频繁重建统计信息 `UPDATE STATISTICS`
- 用 `WITH (NOLOCK)` 需谨慎（会读脏数据）

### 16.6 Oracle 排查与优化

**定位慢 SQL：**

```sql
-- 查看当前会话与 SQL
SELECT sid, serial#, status, sql_id, sql_text
FROM v$session s JOIN v$sql q ON s.sql_id = q.sql_id
WHERE status = 'ACTIVE';

-- 查看最耗时的历史 SQL
SELECT sql_id, executions, elapsed_time, cpu_time, sql_text
FROM v$sql
ORDER BY elapsed_time DESC
FETCH FIRST 10 ROWS ONLY;
```

**执行计划与统计信息：**

```sql
-- 查看执行计划
EXPLAIN PLAN FOR SELECT ...;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- 收集统计信息（执行计划失真的根源）
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS('SCHEMA', 'TABLE_NAME');
END;
```

**Oracle 专属工具：**

| 工具 | 用途 |
|------|------|
| **AWR 报告** | 整体性能快照分析（`@?/rdbms/admin/awrrpt.sql`） |
| **ASH 报告** | 实时会话级分析 |
| **SQL Monitor** | 单个 SQL 详细监控 |
| **ADDM** | 自动诊断建议 |

**注意：** Oracle 默认 `READ COMMITTED`，多版本并发（MVCC）与 MySQL 不同，锁竞争分析需看 `v$lock`、`v$locked_object`。

### 16.7 国产数据库优化要点

| 数据库 | 排查工具 | 对标 |
|------|------|------|
| **达梦 DM** | `EXPLAIN`、`ET` 工具、AWR 报告、`V$SQL` | 对标 Oracle |
| **KingbaseES** | `EXPLAIN ANALYZE`、`ksql`、`sys_stat_statements` | 对标 PostgreSQL |
| **openGauss** | `EXPLAIN ANALYZE`、WDR 报告、`dbe_perf` 视图 | 对标 PostgreSQL |
| **TiDB** | `EXPLAIN ANALYZE`、慢查询日志、TiDB Dashboard | 对标 MySQL |
| **OceanBase** | `EXPLAIN`、OCP 监控、SQL 审计 | 对标 MySQL/Oracle |

> **国产库优化基本遵循对标源库的方法**：达梦/神通 → 参照 Oracle 的 AWR、统计信息、执行计划；金仓/openGauss/瀚高 → 参照 PostgreSQL 的 `EXPLAIN ANALYZE`、`VACUUM`、`ANALYZE`；TiDB/OceanBase(MySQL 模式) → 参照 MySQL 的 `EXPLAIN`、慢查询日志。

### 16.8 通用 SQL 优化清单

以下优化项**对所有数据库都适用**：

| # | 优化项 | 说明 |
|---|------|------|
| 1 | 避免 `SELECT *` | 只取需要的列，减少 IO 和网络传输 |
| 2 | 不在索引列上做运算 | `WHERE YEAR(create_time)=2024` 导致索引失效，改为 `WHERE create_time BETWEEN ...` |
| 3 | 避免隐式类型转换 | `WHERE id = '100'`（id 是数字）会失效，保持类型一致 |
| 4 | 避免前导通配符 | `LIKE '%xxx'` 无法用索引，`LIKE 'xxx%'` 可以 |
| 5 | 用 `IN`/`UNION` 替代 `OR` | `OR` 常导致索引失效 |
| 6 | 合理分页 | 深分页用游标法（`WHERE id > 上次值`） |
| 7 | 大表 JOIN 先过滤 | 子查询/CTE 先缩小结果集再 JOIN |
| 8 | 缩短事务 | 减少锁持有时间，避免长事务 |
| 9 | 批量而非逐条 | 用批量插入/更新替代循环单条 |
| 10 | 定期更新统计信息 | 保证执行计划准确 |

### 16.9 索引优化原则

**建索引的时机：**

- WHERE / JOIN / ORDER BY / GROUP BY 频繁使用的列
- 选择性高的列（重复值少的列）
- 覆盖查询所需列（覆盖索引）

**不建索引的时机：**

- 数据量很小的表（全表扫描反而更快）
- 频繁增删改的表（索引维护成本高）
- 选择性极低的列（如「性别」只有两个值）

**复合索引顺序：**

- 遵循「最左前缀」原则
- 把**区分度高**、**经常用于等值查询**的列放前面
- 范围查询的列放最后

```sql
-- 正确示例：等值在前，范围在后
CREATE INDEX idx_orders ON orders(user_id, status, create_time);
-- 可命中：WHERE user_id=? AND status=? AND create_time>?
-- 可命中：WHERE user_id=?
-- 不可命中：WHERE create_time>? （未用最左列 user_id）
```

## 附：核心差异速查表（一页纸）

| 功能 | MySQL | PostgreSQL | SQL Server | Oracle | 国产库对标 |
|------|------|------|------|------|------|
| 分页 | `LIMIT m,n` | `LIMIT n OFFSET m` | `OFFSET..FETCH` | `OFFSET..FETCH` | 随兼容源 |
| 限制行数 | `LIMIT n` | `LIMIT n` | `TOP n` | `FETCH FIRST n` | 随兼容源 |
| 自增 | `AUTO_INCREMENT` | `SERIAL` | `IDENTITY(1,1)` | `SEQUENCE` | 随兼容源 |
| 当前时间 | `NOW()` | `NOW()` | `GETDATE()` | `SYSDATE` | 随兼容源 |
| 空值替换 | `IFNULL` | `COALESCE` | `ISNULL` | `NVL` | 随兼容源 |
| 拼接 | `CONCAT()` | `\|\|` | `+` | `\|\|` | 随兼容源 |
| 截取 | `SUBSTRING` | `SUBSTRING` | `SUBSTRING` | `SUBSTR` | 随兼容源 |
